PLANEJADOR DE ESTUDOS — PWA V5 COM CADASTRO MANUAL, EXCEL E IA ATUALIZADA

CONTEÚDO DO PACOTE
- index.html: Planejador de Estudos PWA V5 (inclui cadastro manual de conteúdo, importação Excel/CSV/JSON, análise hierárquica por IA, painéis de estudos e PWA).
- manifest.webmanifest: configuração de instalação como PWA.
- service-worker.js: cache básico do app e atualização de versão; não armazena URLs de retorno OAuth.
- icons/: ícones 192x192 e 512x512.
- VERIFICAR_RLS_SUPABASE.sql: consulta de verificação, somente leitura.
- CONFIGURAR_TABELA_SE_NECESSARIO.sql: SQL opcional, apenas se a tabela de estudos ainda não existir.

RECURSOS PRINCIPAIS
- Os painéis “Últimos estudos” e “Sugestões para os próximos estudos” aparecem lado a lado (em telas largas) e acima do progresso por prioridade e disciplina.
- O painel de sugestões mostra até quatro disciplinas pendentes e segue a estratégia escolhida em Personalização: “Prioridade primeiro”, “Prioridade + progresso” ou “Prioridade + data”.
- Em “Prioridade + data”, a sugestão dentro de cada prioridade começa pelas disciplinas nunca estudadas e depois pelas há mais tempo sem estudo.
- O quadro fixo “Pesos & Questões” foi removido porque mostrava valores estáticos de uma prova. O cronograma de datas continua no Dashboard.
- A tabela extensa com Status, Prioridade, Disciplina, Tópico, Subtópico, Peso Edital, Horas, Questões e Ações foi removida da tela principal. O acompanhamento de conclusão fica no quadro recolhível “Progresso por prioridade e disciplina”; o conteúdo detalhado permanece na aba “Edital Verticalizado”.
- Os botões Resetar, Exportar e Importar foram mantidos em uma barra compacta. O atalho “Estudar” nas sugestões abre o Registro de Estudos e seleciona a disciplina; anotações continuam acessíveis no painel de progresso.
- O botão superior de armazenamento mostra “Nuvem” ou “Local” e a data/hora do último salvamento confirmado. Ao alterar dados com conta conectada, aparece “Local” até a sincronização com a nuvem ser confirmada.
- O cache do service worker foi atualizado para forçar a atualização da interface quando a nova publicação for carregada.

PUBLICAR / INSTALAR
1. Extraia o ZIP.
2. Publique TODOS os arquivos e a pasta icons/ no mesmo diretório de um site HTTPS (por exemplo, Netlify ou GitHub Pages). index.html, manifest.webmanifest e service-worker.js devem ficar na raiz da publicação.
3. Não abra index.html diretamente com file:// para autenticar. OAuth e service worker precisam de HTTPS ou localhost.
4. Acesse o endereço publicado. Informe a URL e a chave pública do projeto Supabase Nutri. Essa configuração fica salva no navegador.
5. Clique em “Continuar com Google” ou use e-mail e senha. Ambos permanecem disponíveis.
6. Depois de autenticar, se já houver um registro na nuvem, a aplicação orienta a baixar os dados remotos ou enviar os dados locais. Leia a mensagem com cuidado para evitar sobrescrever progresso.
7. Para instalar no celular, abra o endereço HTTPS no navegador e use “Instalar”/“Adicionar à tela inicial” quando a opção aparecer.

CONFIGURAR GOOGLE OAUTH NO SUPABASE
A) No Supabase, abra Authentication → Sign In / Providers → Google. Ative o provedor. Se ele já estiver habilitado para o Diário Nutricional no MESMO projeto Nutri, não é necessário criar outro projeto Supabase.
B) No Google Cloud / Google Auth Platform, o OAuth Client precisa ser do tipo Web application. Em Authorized redirect URIs, use o Callback URL que o painel do provedor Google do Supabase mostrar (normalmente https://<project-ref>.supabase.co/auth/v1/callback). O Client ID e Client Secret ficam no painel do Supabase; nunca os coloque no HTML.
C) Em Supabase → Authentication → URL Configuration, mantenha o Site URL oficial e acrescente a URL real do Planejador à lista Redirect URLs. Para uma publicação em pasta, permita o caminho exato ou um padrão restrito, por exemplo https://seu-dominio/planejador/**. Não use o domínio de exemplo literalmente.
D) A URL de retorno solicitada pelo Planejador é a origem + caminho atuais, sem query string. Esse endereço deve corresponder a uma Redirect URL permitida pelo Supabase.
E) Erros como “redirect URL not allowed” indicam que a URL publicada precisa ser acrescentada em Authentication → URL Configuration. “Provider not enabled” indica que o Google precisa ser habilitado em Sign In / Providers.

SUPABASE / TABELA
- O Planejador usa o projeto Nutri existente e a tabela public.study_planner_data. Ele NÃO usa a tabela diary_data do Diário Nutricional; cada aplicativo mantém seus próprios registros.
- A estrutura esperada é user_id (uuid, chave primária e referência a auth.users), data (jsonb) e updated_at (timestamptz).
- Use VERIFICAR_RLS_SUPABASE.sql no SQL Editor para conferir se a tabela existe, se RLS está habilitado e quais políticas existem.
- CONFIGURAR_TABELA_SE_NECESSARIO.sql é opcional: execute apenas se a tabela ainda não existir ou precisar ser criada. Antes de alterar políticas já existentes, examine o resultado do SQL de verificação.
- As políticas devem garantir auth.uid() = user_id para leitura, inserção, atualização e exclusão. A chave do navegador deve ser somente publishable/anon, nunca service_role ou segredo privado.

DADOS LOCAIS E PRIVACIDADE
- A sessão Supabase fica persistida pelo cliente de autenticação neste dispositivo.
- O aplicativo guarda cópias locais por usuário do Supabase. Ao alternar entre contas no mesmo navegador, tenta recuperar a cópia local da conta correspondente; se não houver, inicia uma cópia local limpa do edital-base antes de oferecer a sincronização.
- A segurança real dos dados remotos depende das políticas RLS no Supabase, não somente da tela de login.
- A instalação PWA usa uma cache shell. A autenticação e a sincronização exigem internet. O cache offline não garante funcionamento das bibliotecas de terceiros quando não houver conexão.
